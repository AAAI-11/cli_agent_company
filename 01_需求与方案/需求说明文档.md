## 3. 功能需求（按优先级）

### P0 —— MVP 必须完成

| 编号 | 功能 | 需求说明 |
|---|---|---|
| F01 | 实时状态可视化 | 屏幕以宠物动画/表情/颜色/文字显示 Agent 状态：thinking、working、waiting_confirm、done、error |
| F02 | Session 气泡 | 只展示当前活跃的 Agent Session；活跃 Session 持续接收状态更新；done/error 保留约 60 秒后消失 |
| F03 | 一键确认（Yes） | Agent 发起关键操作确认时，用户按下实体 Yes 键即可授权继续 |
| F04 | 实体输入 | 至少包含 Yes 确认键和语音 PTT 键；按键支持短按/长按可配置 |
| F05 | USB 直连通信 | PC 与设备通过 USB 串行协议同步状态、按键事件、配置和资源，不依赖局域网 |
| F06 | 桌面端管理 | PC 桌面端负责 Agent 适配、状态归一化、设备连接管理、固件升级和基础配置 |

### P1 —— 进阶功能

| 编号 | 功能 | 需求说明 |
|---|---|---|
| F07 | 语音交互输入（PTT） | 按住语音键录音，松开后由桌面端 ASR 识别为文字，并注入当前 Agent Session |
| F08 | 可更换显示主题/形象 | 支持至少一个固定形象槽 + 一个可替换形象槽；PC 端完成图片/视频转码、校验后同步到设备 |
| F09 | 摇杆交互与 Session 切换 | 四向摇杆/中键用于切换 Session、控制 UI 和触发可配置动作 |
| F10 | 按键/摇杆自定义 | 按键和摇杆的短按/长按动作可由用户在桌面端配置并持久化到设备 |

### P2 —— 扩展功能

| 编号 | 功能 | 需求说明 |
|---|---|---|
| F11 | 多终端协同显示 | 多台设备连接同一 PC，按角色/分组显示不同 Agent 或不同维度 |
| F12 | 实用小组件 | 空闲时轮播番茄钟、喝水提醒、任务耗时、Token 仪表盘等 |
| F13 | PetUI 组件中心 | 支持通过 Agent Skill 生成/校验/发布小组件，并从桌面端同步到设备 |
| F14 | 无线扩展（可选） | 在 USB 直连基础上，预留 Wi-Fi/Thread 扩展能力，用于“离开电脑仍能感知”的场景 |

> **MVP 范围**：F01～F06。P1/P2 功能不进入 MVP 关键路径。

## 4. 系统总体架构

```text
AI Agent（Claude Code / Codex / Cursor ...）
   │  日志 / Hook / 回调
   ▼
桌面端（Tauri + React）
   ├─ Bridge sidecar：Agent 适配、状态归一化、Session 管理
   ├─ ASR 服务：语音识别
   ├─ 形象管理：生成 / 导入 / 转码 / 校验 / 同步
   ├─ PetUI 组件中心：安装 / 移除 / 校验 / 同步
   └─ USB 设备管理：发现 / 连接 / 固件升级 / 诊断
        │  USB 串行协议
        ▼
ESP32-P4 设备
   ├─ 480×640 MIPI 高分屏：宠物动画 / 气泡 / 组件
   ├─ 实体按键 + 四向摇杆：输入事件上报
   ├─ 麦克风：录音上传
   └─ PetUI 运行时：加载主题包和组件包
```

### 设计原则

1. **PC 是 Agent 路由中心**：所有 Agent 适配、状态语义、ASR、资源处理都放在桌面端；
2. **设备是薄客户端**：设备只负责显示、输入、录音和资源加载；
3. **USB 直连优先**：MVP 不引入 Wi-Fi/MQTT，降低配网、断线、安全等复杂度；
4. **资源包原子化**：形象和组件以“包”为单位传输、校验、切换，避免设备状态损坏。

## 5. 硬件需求

### 5.1 推荐硬件方案（参考 HachimoDock）

| 模块 | 推荐方案 | 说明 |
|---|---|---|
| 主控 | ESP32-P4 | RISC-V 双核，性能足以支撑高分屏动画、输入和 PetUI 运行时 |
| 存储 | 32MB Flash + 32MB PSRAM | 承载固件、默认形象、可替换形象和组件资源 |
| 屏幕 | 2.8 英寸 480×640 MIPI-DSI 竖屏 | 高分屏才能呈现有吸引力的宠物动画和组件 UI |
| 输入 | 3 个实体按键 + 1 个四向中按摇杆 | 覆盖 Yes、PTT、自定义动作和 Session 切换 |
| 音频 | 板载 MEMS 麦克风 | 用于 PTT 语音采集 |
| 连接 | USB-UART 日常通信 + 烧录；硬件保留 USB HS OTG 能力 | MVP 使用 USB 直连，不依赖 Wi-Fi |
| 外壳 | 3D 打印（FDM） | 预留屏幕、按键、摇杆、Type-C 开孔 |

### 5.2 最低可接受硬件（降级方案）

若 ESP32-P4 或 MIPI 屏暂时不可得，可降级为：

- ESP32-S3 + 8MB PSRAM；
- 240×320 SPI（ST7789）屏幕；
- USB-UART 通信；
- 保留 Yes 键和 PTT 键，暂不做摇杆。

降级方案仅用于原型验证，不作为最终产品目标。

## 6. 软件需求

### 6.1 桌面端（Tauri + React + Bridge sidecar）

- 提供设备管理界面：连接状态、固件版本、资源状态、传输进度、诊断信息；
- Agent 跟随：读取并归一化 ChatGPT（Codex）、Claude 等 Agent Session；
- Session 管理：维护活跃 Session 列表，生成设备气泡；
- ASR 服务：接收设备录音，调用本地或云端语音识别，将文本路由到对应 Agent；
- 形象管理：支持内置形象、本地导入、AI 生成、社区导入，并在传输前完成裁切/转码/校验；
- PetUI 组件中心：管理组件安装、移除、预览、同步和容量校验；
- 按键/摇杆配置：允许用户自定义短按/长按动作。

### 6.2 设备固件（ESP-IDF + FreeRTOS）

- MIPI 屏驱动 + UI 渲染；
- PetUI 运行时：加载 Manifest、状态机、按钮映射和资源；
- 输入管理：按键/摇杆事件采集与上报；
- 音频采集：I2S 录音并上传；
- USB 协议解析：接收状态、配置、形象和组件包；
- 资源双槽管理：固定槽 + 可替换槽，切换时原子操作；
- OTA/固件升级支持。

### 6.3 USB 通信协议

- 协议类型：基于 USB 串行通道的二进制/JSON 混合协议；
- 高频小消息（状态、按键事件）使用轻量 JSON 或二进制帧；
- 大资源（形象包、组件包、固件）使用分块传输 + 校验；
- 所有写设备操作支持 ACK/失败重传，避免资源损坏。

## 7. 非功能需求

| 类别 | 需求 |
|---|---|
| 实时性 | 状态变化到屏幕显示延迟 < 500ms；按键事件到 PC 确认 < 200ms |
| 稳定性 | USB 断开/重连后自动恢复；设备固件异常可恢复出厂 |
| 易用性 | 桌面端免命令行即可完成连接、升级、形象和组件同步 |
| 安全性 | API Key 只保存在本机桌面端配置中，不写入固件和仓库 |
| 可扩展性 | 协议预留多设备、无线传输、新 Agent 适配能力 |
| 可维护性 | 支持 OTA 固件升级和资源包原子更新 |

## 8. 兼容性需求（为后期特色预留）

> 后期可能加入本地隐私、多 Agent 开放适配、低成本教学套件、状态数据增强、PetUI 组件生态、多模态交互等特色。以下兼容性要求用于保证这些特色可以在不推翻现有架构的前提下逐步加入。

### 8.1 硬件兼容

- 主控兼容：核心业务逻辑与具体主控解耦，至少兼容目标主控 ESP32-P4 和降级主控 ESP32-S3；
- 屏幕兼容：UI 层抽象分辨率和驱动接口，目标 480×640 MIPI，降级 240×320 SPI；资源包需支持分辨率适配或明确拒绝不兼容资源；
- 输入兼容：按键、摇杆、触摸（可选）统一抽象为输入事件；无摇杆设备也应能完成 P0 核心功能；
- 音频兼容：I2S 麦克风接口抽象，可替换 INMP441 或其他 I2S/模拟麦克风方案；
- 连接兼容：USB 串口为主，硬件和协议预留 Wi-Fi/Thread 等无线扩展位，不影响现有 USB 使用。

### 8.2 Agent 兼容

- MVP 至少支持 1 种 Agent，但架构上必须支持多 Agent 适配器；
- 状态语义统一为 thinking / working / waiting_confirm / done / error，不绑定任何单一 Agent 的私有输出；
- 预留 Agent Hook、日志解析、CLI 输出、插件 SDK 等多种接入方式；
- 后续新增 Cursor、Aider、Gemini CLI、GitHub Copilot CLI 等 Agent 时，只增加 Adapter，不修改设备固件。

### 8.3 桌面端与操作系统兼容

- 桌面端优先支持 macOS（Apple Silicon）和 Windows x64；如条件允许，支持 Linux；
- 串口发现、设备连接、资源传输必须使用跨平台方案；
- 不依赖特定终端模拟器；Agent 状态获取和指令注入通过 Bridge 适配层完成。

### 8.4 协议与数据格式兼容

- USB 通信协议必须带版本号，支持向前/向后兼容；
- 新增协议字段时，旧设备可忽略未知字段；旧桌面端连接新设备时给出固件升级提示；
- 主题包/组件包必须包含 manifest、schema 版本和校验信息；不兼容包拒绝安装并返回原因；
- 图片、视频、音频等资源统一在桌面端转码，设备只接受白名单格式。

### 8.5 服务与 API 兼容

- ASR 服务可插拔：本地 Whisper / faster-whisper、云端 ASR 通过统一接口切换；
- 形象生成服务可插拔：内置素材、本地生成、AI 生成、社区导入均可作为来源；
- PetUI 组件 Skill 输出必须经过统一校验，兼容未来新增组件类型；
- API Key 等敏感信息只保存在桌面端本机配置中，不写入固件或仓库。

### 8.6 版本演进兼容

- 固件 OTA 升级后保留用户配置、已安装形象和组件；跨版本资源自动迁移或重新同步；
- 桌面端升级不强制要求设备同时升级；协议不兼容时明确提示并给出升级路径；
- 后续加入无线多终端时，现有 USB 协议、设备注册和资源管理逻辑应能复用或平滑扩展。

### 8.7 硬件已定型约束（PCB 基线）

- 当前 PCB 已经完成设计/绘制，后续以“不改主板、不重新打样”为首要原则；
- 后期特色应优先通过桌面端、固件 OTA、USB 协议和资源包实现，不依赖硬件改动；
- 若确需新增硬件能力，优先使用预留接口、扩展板或模块化子板，避免修改主 PCB；
- 新功能上板前必须确认当前 PCB 是否已预留对应 GPIO、电源和通信接口；未预留的硬件功能列入“硬件改版”清单，不作为当前版本承诺；
- 在仓库中记录当前 PCB 的可用资源（已用引脚、空闲引脚、可用接口、供电能力），作为后续兼容性评估依据；
- 任何硬件改动需走变更评估：影响范围、重新打样成本、交期、固件/结构/测试同步修改。

## 10. 风险与降级策略

| 风险 | 应对 |
|---|---|
| ESP32-P4 / MIPI 屏采购困难 | 先用 ESP32-S3 + SPI 屏做原型，保留 USB 直连和分层架构 |
| 高分屏动画开发量大 | MVP 先用静态表情/颜色/文字，后续再逐步替换为完整动画 |
| 多 Agent 适配复杂 | 先只适配 1 个 Agent，Bridge 层抽象后逐步扩展 |
| USB 驱动/跨平台兼容问题 | 优先支持 macOS + Windows；使用成熟串口库和自动发现机制 |
| 组件运行时工作量过大 | P2 阶段先做内置小组件，PetUI 组件中心延后 |

## 12. 总结

本版本在保留原开题报告“Agent 状态可视化 + 物理交互”核心需求的基础上，将技术路线优化为：

- **硬件**：ESP32-P4 + 480×640 MIPI 高分屏 + 按键/摇杆 + 麦克风；
- **连接**：MVP 使用 USB 直连，P2 再考虑无线扩展；
- **软件**：Tauri + React 桌面端 + Bridge sidecar + ESP32-P4 PetUI 固件；
- **原则**：PC 中心化路由、设备薄客户端、资源包原子化。

该方案优先保障单设备核心体验，避免用 P2 多终端需求绑架 MVP，同时为后续多终端、组件生态和无线扩展保留清晰路径。
